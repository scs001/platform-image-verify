# scheduling-cluster-aware Specification

## Purpose

Enhances scheduling tools with cluster context, enabling coordinated task execution across multiple agents in a cluster.

## ADDED Requirements

### Requirement: Cluster-aware scheduling tools

The scheduling tools (create, list, pause, delete) SHALL be extended with cluster-aware fields:

**Create tool input:**
```typescript
{
  schedule: string;           // cron expression or one-shot timestamp
  promptTemplate: string;     // prompt to execute on each run
  clusterId?: string;         // optional: cluster to use instead of single agent
  
  executionPolicy?: {
    allowParallel?: boolean;  // allow multiple agents to run concurrently (default: false)
    timeoutMinutes?: number;  // max duration per agent (default: cluster's schedulingPolicy.maxConcurrentRuns)
    fallbackAgent?: string;   // agent to use if primary fails (optional)
    resultAggregation?: "first" | "all" | "summary";  // how to combine results (default: "all")
  };
  
  targetAgents?: string[];    // override which agents in the cluster to run (default: all defaultAgents)
}
```

**Create tool response:**
```typescript
{
  taskId: string;
  status: "created";
  clusterId?: string;
  scheduledAt: string;
  nextRunAt: string;
  agents: string[];           // list of agents that will execute
  policy: ExecutionPolicy;    // copy of execution policy
}
```

When `clusterId` is provided:
- The task SHALL be associated with the cluster, not a single agent
- On each scheduled run, ALL target agents SHALL be invoked (unless `allowParallel: false`, then they run sequentially)
- Results SHALL be aggregated according to `resultAggregation` policy
- The task's `list` entry SHALL show cluster name and agent count

When `clusterId` is omitted:
- Existing single-agent behavior is preserved (backward compatible)

#### Scenario: Cluster task creation

- **WHEN** an agent calls the create tool with `clusterId` and `targetAgents: ["finance-bot", "data-analyst"]`
- **THEN** a task is created that will invoke both agents on each scheduled run

#### Scenario: Parallel execution policy

- **WHEN** a cluster task has `executionPolicy.allowParallel: true`
- **THEN** all target agents are invoked concurrently; the task's duration is the max of individual agent durations

#### Scenario: Sequential execution policy

- **WHEN** a cluster task has `executionPolicy.allowParallel: false` (default)
- **THEN** agents are invoked sequentially in the order they appear in `targetAgents`; the task's duration is the sum of individual durations

#### Scenario: Result aggregation

- **WHEN** a cluster task completes with `resultAggregation: "summary"`
- **THEN** the task result includes a combined summary generated by a designated summarizer agent (first agent in `targetAgents`)

### Requirement: Cluster task listing and management

The list tool SHALL return tasks with cluster context:

```typescript
{
  tasks: Array<{
    taskId: string;
    status: "active" | "paused" | "completed";
    clusterId?: string;
    clusterName?: string;      // only present if cluster task
    agentCount: number;        // number of agents involved
    schedule: string;
    nextRunAt: string;
    lastRunAt?: string;
    lastResult?: string;       // preview of last execution result
  }>;
}
```

Pause and delete operations SHALL work at the cluster-task level:
- Pausing a cluster task SHALL stop all future executions for all agents in the cluster
- Deleting a cluster task SHALL remove the task entirely; in-flight executions SHALL complete normally

#### Scenario: Cluster task listed with metadata

- **WHEN** an agent calls the list tool
- **THEN** cluster tasks show `clusterName` and `agentCount` fields

#### Scenario: Pause cluster task

- **WHEN** a user pauses a cluster task via the UI
- **THEN** all agents in the cluster stop executing until the task is resumed

### Requirement: Task history with cluster view

The task history page SHALL display cluster tasks with:
- A cluster badge showing the cluster name and icon
- Agent avatars for all participating agents
- Aggregate metrics: total duration, tokens used across all agents, success/failure status
- Individual agent results expandable/collapsible

For cluster tasks, the detail view SHALL show:
- Timeline of agent executions (sequential or parallel visualization)
- Per-agent output and token usage
- Aggregated result (if applicable)

#### Scenario: Cluster task history displayed

- **WHEN** a user opens the task history page
- **THEN** cluster tasks are visually distinguished with cluster badges and agent avatars

#### Scenario: Parallel execution timeline

- **WHEN** a user views details of a parallel cluster task
- **THEN** the timeline shows all agents executing simultaneously, with start/end times aligned

### Requirement: Cluster-wide task control

The platform SHALL expose endpoints for cluster-wide task management:

**POST /api/clusters/:clusterId/schedule**
- Create a new task bound to this cluster
- Same body as create tool, but clusterId is inferred from path
- Response: Task object with taskId

**POST /api/clusters/:clusterId/tasks/:taskId/pause**
- Pause a specific task in this cluster
- Response: `success: true`

**POST /api/clusters/:clusterId/tasks/:taskId/resume**
- Resume a paused task
- Response: `success: true`

**DELETE /api/clusters/:clusterId/tasks/:taskId**
- Delete a task from this cluster
- Response: `success: true`

**GET /api/clusters/:clusterId/tasks**
- List all tasks associated with this cluster
- Response: Array of task objects

#### Scenario: Cluster-level task creation

- **WHEN** a user creates a task via POST /api/clusters/:id/schedule
- **THEN** the task is automatically bound to the cluster and inherits its scheduling policy
